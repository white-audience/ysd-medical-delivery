# AI-RAG 检索设计与评测

> 日期：2026-10-21  
> 范围：`ysd-ai-service`（RAG 知识库、检索参数、评测脚本）  
> 目标：用真实医药业务知识替换项目 README，建立 20 题评测集，验证 RAG 召回与拒答能力，并留存可复现的证据。

---

## 1. 方案概览

### 1.1 检索链路

```text
classpath:rag/*.md
  │ MarkdownDocumentReader 逐份读取
  ▼
TokenTextSplitter（chunk=500 tokens，min=100 chars）
  │ 每个 chunk 正文前加「【文档：文件名】」来源标记
  ▼
bge-m3（Ollama，1024 维）向量化
  ▼
Redis Stack（RediSearch + HNSW，COSINE）
  │ FT.SEARCH，topK=4，similarityThreshold=0.5
  ▼
QuestionAnswerAdvisor → 拼接上下文 → DeepSeek deepseek-chat
```

### 1.2 关键参数

| 参数 | 值 | 说明 |
| --- | --- | --- |
| Embedding 模型 | `bge-m3`（Ollama） | 1024 维，中文语义检索表现稳定 |
| Chat 模型 | `deepseek-chat` | 走 OpenAI 兼容协议 |
| 向量库 | Redis Stack `ysd_rag_idx` | HNSW，COSINE，前缀 `ysd:rag:` |
| Chunk size | 500 tokens | 医药规则类文档按小节切分，单 chunk 通常 1—2 个知识点 |
| `topK` | 4 | 兼顾召回与上下文 Token |
| `similarityThreshold` | 0.5 | 初始值，调参见第 5 节 |

参数已外置到 `ysd-ai-service/src/main/resources/application.yml`：

```yaml
rag:
  search:
    top-k: 4
    similarity-threshold: 0.5
```

### 1.3 本次代码改动

| 文件 | 改动 | 原因 |
| --- | --- | --- |
| `rag/` 目录 | 删除 README 拷贝，新增 8 份医药业务文档 | 原知识库只有工程 README，检索结果与业务无关 |
| `RagDataLoader.java` | 逐份读取文档；chunk 正文前拼接 `【文档：文件名】`；启动时清理旧向量 | ① 保证来源可追溯；② 防止重复灌入 |
| `AiDrugController.java` | RAG 参数外置；新增 `GET /ai/drug/debug/retrieve` 检索诊断接口 | 评测/调参时只调用向量检索，不消耗大模型 Token |
| `RetrievedChunkVO.java` | 新增检索结果 VO（id/score/source/text/metadata） | 为评测脚本提供召回证据 |

**为什么把文件名写进正文**：Spring AI 1.1.8 的 `RedisVectorStore` 检索时只回传建了索引的 `content` / `embedding` 字段，写入时附加的自定义 metadata（如 `source`）不会随搜索结果返回。把来源拼进 chunk 正文是成本最低、且线上回答同样受益的做法。

### 4.3 失败/部分正确分析

**P03（⚠️）**：召回命中了正确的《处方药购买规则》，但 Top-4 未包含“审核不通过的常见原因”那个 chunk（该 chunk 排名第 6，相似度 0.8302）。因此回答只给出“审核未通过”这一层，缺少处方过期、姓名不一致、超量、来源无法核验等具体原因。

可选的改进方式：

1. `topK` 提到 6：能把第 6 名 chunk 纳入上下文，但上下文 Token 增加约 50%；
2. 把“审核不通过原因”并入“购买流程”小节，让一个 chunk 同时包含流程和失败原因；
3. 对高频规则类问题增加 query 改写或 rerank。

本次未修改默认参数，原因见下一节：该项属于“回答不够完整”，不影响核心结论，且提高 `topK` 会牺牲成本。

## 5. 调参记录

由于初始参数下准确率 95%（≥70% 目标），**不需要为达标而调参**。为确认参数边界，仍对检索层做了对比（只跑检索、不调用大模型，避免成本与随机性）：

| topK | threshold | Hit Rate @ K | 平均召回片段数 | 说明 |
| --- | --- | --- | --- | --- |
| 4 | 0.5 | 15/15（100%） | 4.0 | **当前默认值** |
| 4 | 0.6 | 15/15（100%） | 4.0 | 与 0.5 等价，未减少噪声 |
| 4 | 0.7 | 15/15（100%） | 4.0 | 仍等价；最相关片段最低分 0.7836 |
| 4 | 0.75 | 15/15（100%） | 3.8 | 略减噪声，但已非常接近相关片段分数下界 |
| 4 | 0.8 | **13/15（86.7%）** | 2.1 | 丢失 F04（0.7836）和 P01（0.7884），阈值过高 |
| 5 | 0.4 | 15/15（100%） | 5.0 | 召回不变，上下文 Token +25% |

**结论：保留 `topK=4 / threshold=0.5`。**

- 阈值 0.8 会直接损伤召回，说明 0.5 留出的安全余量是必要的；
- 0.75 虽然在本评测集上没有掉召回，但相关片段最低分 0.7836，余量只有 0.03，换一种问法就可能漏召回，不适合作为默认值；
- `topK=5` 没有提升本评测集的 Hit Rate，反而增加 25% 上下文；P03 需要 `topK=6` 才能纳入目标 chunk，成本更高，暂不采用。

> 注意：20 题样本量较小，以上阈值只在本知识库和本 embedding 模型下标定。知识库扩量后应重新评测，不能直接照搬。

## 6. 结论与边界

### 6.1 已验证的能力

1. **事实检索可靠**：15 道有答案的问题 Hit Rate@4 = 100%，Top-1 平均相似度 0.847，说明 bge-m3 + 500 token 切分适合这类短规则文档。
2. **边界拒答稳定**：孕期用药、开方、儿童剂量、抗凝联用、疾病诊断 5 题全部拒绝了个体化结论，并引导至医生/药师；没有出现编造剂量或诊断的情况。
3. **工具与 RAG 能协同**：药品事实优先走 `queryDrugInfo`，平台规则走 RAG；工具字段缺失时（如蒙脱石散适应症为“暂无”），模型能回退到文档并如实说明数据缺失（F10）。
4. **来源可追溯**：每个 chunk 带 `【文档：文件名】`，回答可以指出依据的文档，评测也能自动判断召回是否命中。

### 6.2 当前方案的边界

- **单轮检索，无多跳**：一次问答只做一次向量检索，最多 4 个片段。像 P03 这种“原因+处理”需要同一文档内多个小节的问题，可能只召回其中一部分。
- **无 rerank**：纯向量相似度排序，缺少 cross-encoder 重排；相似度接近时排序不稳定（P03 目标 chunk 排第 6，仅比第 4 名低 0.0036）。
- **知识库无版本与权限**：所有文档对所有用户可见，没有按门店、地区、药品目录做过滤；文档更新需要重启服务重新灌入。
- **规则类问题依赖文档写法**：答案是否完整，很大程度取决于文档是否把同一主题写在同一个 chunk 里；切分策略比模型能力更影响结果。
- **医疗建议必须人工兜底**：平台不诊断、不开方、不给个体化剂量。特殊人群、复杂联合用药、急症必须由医生处理；RAG 只能提供规则和说明书级别的事实。
- **评测集规模有限**：20 题覆盖了主要场景，但不足以证明长尾问题；判定含人工主观成分，未接入 LLM-as-judge 或人工双盲标注。
- **工具失败会改变回答风格**：本次评测中曾因 `ysd-api` 旧 jar 导致 `/inner/dish/drug/search` 404，模型转而大量使用 RAG 并声明“查询服务不可用”。这类降级是安全的，但会拉低回答完整度，生产环境需要监控工具失败率。

### 6.3 后续可做

1. 引入 rerank（如 bge-reranker）并按“规则类问题”单独调 `topK`；
2. 把“流程 + 失败原因 + 限购”合并为更粗的 chunk，减少同一主题被切散；
3. 扩充到 100+ 题并加入 LLM-as-judge，按类别统计准确率；
4. 知识库加 `version` / `store_id` 元数据，支持增量更新与门店级过滤；
5. 对拒答题增加独立的“安全判定”规则或小模型校验，避免 prompt 退化导致越界。

python docs/05-测试与压测/rag-eval/run_eval.py --top-k 4 --threshold 0.5
