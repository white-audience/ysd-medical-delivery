## 一、现状分析

### 1.1 工程结构

当前是**单体应用 + Maven 多模块**，只有一个可启动进程：

| 模块 | 打包 | 作用 | 可启动 |
|---|---|---|---|
| `ysd-take-out` | pom | 父工程，仅做依赖版本管理 | 否 |
| `ysd-common` | jar | 常量、ThreadLocal 上下文、异常、工具类、配置属性、统一返回 | 否 |
| `ysd-pojo` | jar | entity(11) / dto(21) / vo(17) | 否 |
| `ysd-server` | jar | 全部 Controller / Service / Mapper / 配置 / 定时任务 / WebSocket | **是（8080）** |

`ysd-server` 内部分层：

```

├── controller/admin    9 个（Category/Drug/DrugCombo/Order/Employee/Shop/Report/WorkSpace/Common）
├── controller/user     8 个（User/AddressBook/ShoppingCart/Category/Drug/DrugCombo/Shop/Order）
```

`category` / `drug` / `drug_spec` / `drug_combo` / `drug_combo_item` / `orders` / `order_detail` / `shopping_cart` / `user` / `address_book` / `employee`

**已使用的外部中间件**：MySQL、Redis（DB 10，仅存 `SHOP_STATUS`）。

### 1.2 关键耦合点清单（改造的真正难点）

微服务拆分的技术障碍不在 Controller，而在下面这些**跨域数据访问**。逐条列出并附文件位置：

| # | 耦合点 | 位置 | 问题本质 |
|---|---|---|---|
| C1 | 下单时同时写 `orders`、`order_detail`，读 `address_book`，读+删 `shopping_cart` | `OrderServiceImpl.java:62-120` | 一次操作跨越 4 个域，需要分布式事务 |
| C2 | 分类删除前校验「是否被药品/药品组合引用」 | `CategoryServiceImpl.java:77,84` | 跨服务校验，且存在 TOCTOU 竞态 |
| C3 | 药品删除前校验「是否被药品组合引用」 | `DrugServiceImpl.java:104` | 同上 |
| C4 | 加购时查 `drug`/`drug_combo` 补 name/image/price | `ShoppingCartServiceImpl.java:28,30` | 跨服务读，且**价格未快照**，药品改价会污染历史购物车 |
| C5 | 支付时查 `user` 拿 openid | `OrderServiceImpl.java:131` | 跨服务读 |
| C6 | 再来一单：读 `order_detail` → 写 `shopping_cart` | `OrderServiceImpl.java:300-321` | 跨服务写 |
| C7 | 报表/工作台直接聚合 `orders`/`user`/`drug`/`drug_combo` | `ReportServiceImpl.java:68,109,113,194,281`、`WorkspaceServiceImpl.java:55-156` | **最严重**：跨表 COUNT/SUM/TOP10 聚合 |
| C8 | 药品分页 SQL 关联分类名 | `DrugMapper.xml:20-35`（`left join category`） | 跨服务 JOIN |
| C9 | 药品组合分页 SQL 关联分类名 | `DrugComboMapper.xml:33-55`（`left join category`） | 跨服务 JOIN |
| C10 | 药品组合查询关联 `drug_combo_item` + `drug` | `DrugComboMapper.xml` / `DrugComboItemMapper.xml` | 跨服务 JOIN（若药品独立） |
| C11 | 用户上下文用 `ThreadLocal` | `BaseContext.java`（`ysd-common`） | ThreadLocal 不跨进程、不跨 Feign、不跨异步线程 |
| C12 | 登录态校验用 Servlet 拦截器 | `JwtTokenAdminInterceptor` / `JwtTokenUserInterceptor` | 每个服务都会重复实现，应上移到网关 |
| C13 | WebSocket 会话存在 JVM 静态 Map | `WebSocketServer.java:22` | 多实例部署时群发漏推送 |
| C14 | 订单超时/派送定时任务 | `OrderTask.java:26,51` | 多实例部署时**重复执行** |
| C15 | 营业状态 `SHOP_STATUS` 读写 | `admin/ShopController.java:29`、`user/ShopController.java:27` | 管理端写、用户端读，天然跨服务共享状态 |
| C16 | 所有服务共用 `ysd-pojo` | `ysd-pojo` 模块 | 会退化成「共享领域模型」反模式 |
| C17 | `spring.main.allow-circular-references: true` | `application.yml:8` | 说明已存在循环依赖，拆开后变成更糟的跨服务循环调用 |

### 1.3 顺带发现的既有缺陷（拆分时必须一起修）

1. **`submitOrder` 没有事务**：`OrderServiceImpl.java:61` 用的是 `@Transient`（`java.beans.Transient`，第 29 行 import），而不是 `@Transactional`。这是无效注解，下单过程中途失败会留下脏数据。全项目仅 `AddressBookServiceImpl`、`DrugServiceImpl`、`DrugComboServiceImpl` 有 `@Transactional`。
2. **支付是假实现**：`OrderServiceImpl.payment()` 第 145-163 行硬编码 `ORDERPAID` 并直接改库，绕过了微信支付。改造时应把「支付成功」设计为 MQ 事件。
3. **购物车不存价格**：`ShoppingCart` 实体无 price 快照，`C4` 每次展示都实时查药品价，拆服务后必然踩坑。
4. **密钥硬编码入库**：`application-dev.yml` 中 OSS AccessKey、微信 appid/secret 明文提交到 git。
5. **`spring-boot-starter-data-redis` 未做通用化**：`RedisConfiguration` 用 `RedisTemplate` 原始类型，且只有 `SHOP_STATUS` 一个用途，但它是后续 WebSocket 广播的方案基础。

### 2.3 服务划分方案（两个粒度，按团队能力选）

**方案 A：粗粒度（5 个业务服务）— 学生项目/小团队推荐**

| `ysd-order-service` | 购物车、下单、支付、订单状态机、地址簿、WebSocket | `shopping_cart`/`orders`/`order_detail` | `user/ShoppingCartController`、`admin+OrderController*`、`user/OrderController`、`WebSocketServer`、`OrderTask` |

| `ysd-report-service` | 报表、工作台 | — | `admin/ReportController`、`admin/WorkSpaceController` |

**方案 B：细粒度（8 个业务服务）— 追求领域纯粹**

拆法：`ysd-auth` / `ysd-employee` / `ysd-user` / `ysd-category` / `ysd-drug` / `ysd-drug_combo` / `ysd-cart` / `ysd-order` / `ysd-report` / `ysd-push`。

> ⚠️ **不建议对分类/药品/药品组合做方案 B 的拆法**。理由：`DrugMapper.xml:20`、`DrugComboMapper.xml:33` 三张表之间有 JOIN，且分类删除要校验药品+药品组合（C2/C3），药品组合要聚合药品（C10）。拆开后 C8/C9/C10 的 JOIN 全部变成 Feign 循环调用 + 内存分页，收益远小于成本。**分类/药品/药品组合应视为同一个限界上下文（Catalog）**。
>
> 同理 `shopping_cart` 与 `orders` 不拆（C1/C4/C6 耦合太紧），地址簿与订单也不拆（下单要读地址簿快照）。

**本方案后续以方案 A 为主线展开。**

## 三、数据库改造策略

三个选项，按推荐度排序：

| 方案 | 做法 | 评价 |
|---|---|---|
| **① 同实例分库（推荐）** | 一个 MySQL 实例内建 5 个库：`sky_admin` / `sky_catalog` / `sky_order` / `sky_user` / `sky_report` | 成本低、可强制禁止跨库 JOIN、可独立连接池配置。适合本项目 |
| ② 单库多表 + 逻辑归属 | 保持 `ysd_take_out` 一个库，按服务约定「只读自己表」 | 最省事，但约束靠人守，容易退化成「共享数据库的分布式单体」 |
| ③ 物理分库 | 每服务独立 MySQL 实例 | 生产级做法，本项目过度设计 |

**必须遵守的硬规则**：
- 禁止跨库 JOIN。C8/C9/C10 的 JOIN 必须在代码层解决（见 4.3）。
- 禁止跨库事务。C1 用 Seata 或消息最终一致性（见 4.4）。
- 报表库可用**只读从库**或 CDC（Canal/Debezium）同步，避免直接读业务库。

**必要的表结构变更**：

## 四、关键难点改造方案

### 4.1 统一鉴权与用户上下文透传（C11 + C12）

**问题**：`BaseContext` 是 `ThreadLocal`，只在当前线程有效。拆服务后 `order-service` 调 `user-service`，user-service 的新线程里 `BaseContext.getCurrentId()` 返回 `null`。

**改造三步**：

1. **网关统一校验 JWT**，解析后把身份写入请求头，剥离原始 token：

```java
// ysd-gateway: AuthGlobalFilter
@Component
public class AuthGlobalFilter implements GlobalFilter, Ordered {
    private static final List<String> WHITE_LIST = List.of(
        "/admin/employee/login", "/user/user/login", "/user/shop/status",
        "/notify/", "/doc.html", "/webjars/");

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String path = exchange.getRequest().getURI().getPath();
        if (WHITE_LIST.stream().anyMatch(path::startsWith)) {
            return chain.filter(exchange);
        }
        // 管理端 token 头为 token；用户端为 authentication
        String token = exchange.getRequest().getHeaders().getFirst("token");
        boolean isAdmin = path.startsWith("/admin/");
        if (!isAdmin) {
            token = exchange.getRequest().getHeaders().getFirst("authentication");
        }
        if (token == null) {
            exchange.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED);
            return exchange.getResponse().setComplete();
        }
        try {
            Claims claims = JwtUtil.parseJWT(
                isAdmin ? adminSecretKey : userSecretKey, token);
            String idKey = isAdmin ? JwtClaimsConstant.EMP_ID : JwtClaimsConstant.USER_ID;
            ServerHttpRequest req = exchange.getRequest().mutate()
                .header("X-Identity-Id", claims.get(idKey).toString())
                .header("X-Identity-Type", isAdmin ? "ADMIN" : "USER")
                .build();
            return chain.filter(exchange.mutate().request(req).build());
        } catch (Exception e) {
            exchange.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED);
            return exchange.getResponse().setComplete();
        }
    }

    @Override public int getOrder() { return -100; }
}
```

2. **下游服务用拦截器把请求头还原进 `BaseContext`**（`BaseContext` 保持不变，业务代码零改动）：

```java
// 每个下游服务的 config 包，从原 WebMvcConfiguration 改造而来
@Configuration
public class IdentityConfiguration implements WebMvcConfigurer {
    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(new HandlerInterceptor() {
            @Override
            public boolean preHandle(HttpServletRequest req, HttpServletResponse resp, Object h) {
                String id = req.getHeader("X-Identity-Id");
                if (id != null) BaseContext.setCurrentId(Long.valueOf(id));
                return true;
            }
            @Override
            public void afterCompletion(HttpServletRequest r, HttpServletResponse p, Object h, Exception e) {
                BaseContext.removeCurrentId();   // 必须清理，防线程池串号
            }
        }).addPathPatterns("/**");
    }
}
```

3. **Feign 调用时透传上下文**（否则 A 服务调 B 服务时身份丢失）：

```java
// ysd-common：Feign 拦截器，随 common 包被各服务自动装配
@Configuration
public class FeignIdentityConfig implements RequestInterceptor {
    @Override
    public void apply(RequestTemplate template) {
        Long id = BaseContext.getCurrentId();
        if (id != null) template.header("X-Identity-Id", String.valueOf(id));
    }
}
```

> 注意：`JwtProperties` 中的 `adminSecretKey`/`userSecretKey` 现在被网关独占使用，下游服务不再需要，`application.yml` 中的 `ysd.jwt` 配置应只保留在网关（或 Nacos 共享配置中）。

### 4.2 跨服务同步调用（C2/C3/C4/C5/C6）

在 `ysd-common` 基础上**新增 `ysd-api` 模块**，只放跨服务契约（Feign 接口 + 出入参 DTO），不放大实体：

```
ysd-api/
├── feign/UserClient.java        # getById / getOpenid
├── feign/CatalogClient.java     # getDrugById / getDrugComboById / countDrugByCategory
├── feign/CartClient.java        # listByUser / deleteByUser / batchInsert
├── feign/OrderClient.java       # getByNumber
└── dto/                         # 仅跨服务传递的瘦 DTO
```

示例：

```java
@FeignClient(name = "ysd-catalog-service", path = "/inner/catalog", fallbackFactory = CatalogClientFallback.class)
public interface CatalogClient {
    @GetMapping("/drug/{id}")
    Result<DrugSnapshotDTO> getDrugById(@PathVariable("id") Long id);

    @GetMapping("/drug/countByCategory")
    Result<Integer> countDrugByCategory(@Param("categoryId") Long categoryId);
}
```

逐条对应改造：

| 耦合 | 改造前 | 改造后 |
|---|---|---|
| C2 分类删除校验 | `drugMapper.countByCategoryId` + `drug_comboMapper.countByCategoryId` | **方案 A 下分类/药品/药品组合同属 catalog-service，无需改造**（这也是不建议拆分 Catalog 的原因）。若走方案 B：改为 `catalogClient.countDrugByCategory()`，并接受 TOCTOU 竞态，兜底用外键约束 |
| C3 药品删除校验 | `itemMapper.countByDrugId` | 同属 catalog-service，无需改造 |
| C4 加购补全信息 | 实时 `drugMapper.getById` | ① 表加 name/image/price 快照字段；② 下单前重新校验价格是否变动（价格变更则提示用户），**不要**在展示时实时查 |
| C5 支付查 openid | `userMapper.getById` | `userClient.getById(userId)`，Feign 缓存该结果 |
| C6 再来一单 | 读 order_detail + 写 shopping_cart | `order-service` 内部完成：`cartClient.batchInsert(cartDTOList)` |
| C1 下单跨 4 域 | 单事务 | 见 4.4 |

**内部接口规范**：所有 Feign 目标接口统一挂 `/inner/**` 前缀，网关层**禁止** `/inner/**` 对外（直接 404），避免内部接口被外部调用。

### 4.3 跨库 JOIN 的四种替代（C8/C9/C10）

原 SQL（`DrugMapper.xml:20-35`）：

```sql
select d.*, c.name as categoryName
from drug d left outer join category c on d.category_id = c.id
```

按优先级：

1. **字段冗余（推荐）**：在 `drug`/`drug_combo` 表加 `category_name` 列，分类改名的场景极少，用一个「分类改名」事件异步刷新即可。这是最省事、性能最好的做法，且**保留 PageHelper 分页能力**。
2. **Feign 批量聚合**：查出本页 drug 后，提取 categoryId 集合，**一次** Feign 拿回 `Map<Long,String>` 在内存拼装。注意必须是批量接口，否则 N+1。
3. **读模型表**：建 `drug_view` 冗余表，由 MQ/CDC 维护。
4. **应用层视图（不推荐）**：跨库建视图或同义词 —— MySQL 不支持跨库视图的可靠用法，且破坏服务边界。

**C10（药品组合关联药品）**：若坚持拆 `drug_combo-service`/`drug-service`，药品组合详情需要「药品组合 + 其下药品列表」。此时 `drug_combo_item` 表加 `drug_name`/`drug_price` 快照列，药品组合展示不再依赖 drug 表；仅在下单校验库存/状态时才 Feign 查询。

### 4.4 分布式事务（C1 下单）

`OrderServiceImpl.submitOrder()` 跨了 catalog（校验药品状态）、user（地址簿）、cart（清空购物车）、order（写订单）四域。

**推荐：不用 Seata，用「本地事务 + 消息最终一致性」**，因为：

- 购物车清空**允许失败重试**（下次进入购物车再兜底清理），无需强一致；
- 地址簿是**只读快照**（读到就行，已经冗余进 `orders.consignee`）；
- 药品状态校验是**弱校验**（下单瞬间校验即可，不做库存扣减）；
- 真正的强一致要求只存在于 `orders` + `order_detail` 两张表 —— **它们在同一个库，本地 `@Transactional` 就够**。

改造后：

```java
@Service
public class OrderServiceImpl implements OrderService {

    @Override
    @Transactional(rollbackFor = Exception.class)   // ← 真正生效的事务，修复原 @Transient 缺陷
    public OrderSubmitVO submitOrder(OrdersSubmitDTO dto) {
        Long userId = BaseContext.getCurrentId();

        // 1. 跨服务只读校验（失败即抛异常快速返回）
        AddressBookSnapshotDTO addr = userClient.getAddressBook(dto.getAddressBookId());
        if (addr == null) throw new AddressBookBusinessException(MessageConstant.ADDRESS_BOOK_IS_NULL);

        List<CartItemDTO> cartItems = cartClient.listByUser(userId).getData();
        if (CollectionUtils.isEmpty(cartItems)) throw new ShoppingCartBusinessException(MessageConstant.SHOPPING_CART_IS_NULL);

        // 2. 价格快照 + 二次校验（防止加购后药品改价）
        catalogClient.validateAndPrice(cartItems);

        // 3. 本地事务：orders + order_detail 同库，强一致
        Orders orders = buildOrders(dto, addr, userId);
        orderMapper.insert(orders);
        orderDetailMapper.insertBatch(buildDetails(orders.getId(), cartItems));

        // 4. 跨服务写：事务提交后再发 MQ 清空购物车（失败可重试，最终一致）
        rocketMQTemplate.send("topic-cart-clear",
            MessageBuilder.withPayload(new CartClearEvent(userId, orders.getNumber())).build());

        return buildVO(orders);
    }
}
```

**什么场景才需要 Seata**：如果后续要做「库存扣减」「优惠券核销」这类**必须强一致**的跨服务写，再引入 Seata AT 模式：

```yaml
seata:
  enabled: true
  application-id: ysd-order-service
  tx-service-group: sky_tx_group
  service:
    vgroup-mapping:
      sky_tx_group: default
  registry:
    type: nacos
    nacos:
      server-addr: 127.0.0.1:8848
```
然后用 `@GlobalTransactional` 替代 `@Transactional`。**本项目当前业务不需要，不要为了用而用。**

### 4.5 跨服务分页（隐藏的坑）

PageHelper 依赖 `ThreadLocal` 且分页发生在 SQL 层。**任何跨服务的数据列表都不能用 PageHelper 分页**，因为：

- 若在 A 服务分页后再 Feign 补 B 服务字段 → 可以（只要 B 是批量查询，见 4.3 方案 2）；
- 若需要按 B 服务字段**排序或过滤** → 必须走字段冗余或读模型，Feign 方案无法实现。

逐条检查现有分页接口：

| 接口 | 分页依据 | 结论 |
|---|---|---|
| `DrugServiceImpl.pageQuery`（`DrugServiceImpl.java:80`）| 按 drug 字段分页，仅需 categoryName | ✅ 字段冗余即可 |
| `DrugComboServiceImpl.pageQuery` | 按 drug_combo 字段分页，仅需 categoryName | ✅ 字段冗余即可 |
| `OrderServiceImpl.conditionSearch`（`:329`）| 按 orders 字段分页 | ✅ 同库 |
| `OrderServiceImpl.pageQuery4User`（`:204`）| 按 orders 字段分页 | ✅ 同库 |
| `EmployeeServiceImpl.pageQuery` | employee 单表 | ✅ 单服务 |
| 用户端药品/药品组合列表（按 categoryId 过滤）| 单表 | ✅ 同服务 |

结论：只要 Catalog（分类/药品/药品组合）不拆，**本项目没有真正的跨服务分页问题**。这是方案 A 的一大优势。

### 4.6 定时任务防重（C14）

`OrderTask.java:26` 每分钟处理超时订单、`:51` 每天 1 点处理派送超时订单。order-service 扩到 2 个实例后，任务会**执行两次**（虽然 `update` 幂等，但会出现重复日志/重复退款风险）。

三种做法，按推荐度：

1. **ShedLock（推荐，改动最小）**：

```java
@Scheduled(cron = "0 * * * * ?")
@SchedulerLock(name = "processTimeoutOrder", lockAtMostFor = "50s", lockAtLeastFor = "10s")
public void processTimeoutOrder() { ... }
```
```yaml
shedlock:
  defaults:
    lock-at-most-for: 5m
# 加 @EnableSchedulerLock(defaultLockAtMostFor = "5m")
```

2. **Redisson 分布式锁**：`lock.tryLock(0, 30, TimeUnit.SECONDS)`。
3. **XXL-Job 独立调度中心**：把定时任务从 order-service 抽成独立执行器，运维可视化。生产推荐，本项目偏重。

> 另外建议：**定时任务不要放在 order-service 里**，而是在 order-service 中暴露 `/inner/order/timeout/process` 接口，由外部调度器（XXL-Job / K8s CronJob）调用。这样 order-service 可以纯粹地水平扩容。

### 4.7 WebSocket 多实例推送（C13）

`WebSocketServer.sessionMap` 是 JVM 级静态 Map（`WebSocketServer.java:22`）。若 order-service 部署 2 个实例，微信支付回调可能落在实例 A，而客户端连的是实例 B → **推送丢失**。

**改造方案（Redis Pub/Sub 扇出，改动最小）**：

1. 抽出独立 `ysd-push-service`，只做 WebSocket，独占 `/ws/{sid}` 路由：

```java
@ServerEndpoint("/ws/{sid}")
@Component
public class WebSocketServer {
    private static final Map<String, Session> SESSION_MAP = new ConcurrentHashMap<>();

    @OnOpen
    public void onOpen(Session session, @PathParam("sid") String sid) {
        SESSION_MAP.put(sid, session);
    }
    @OnClose
    public void onClose(@PathParam("sid") String sid) { SESSION_MAP.remove(sid); }

    /** 只负责把本实例的会话发出去 */
    public void sendToAllLocalClient(String message) {
        SESSION_MAP.values().forEach(s -> {
            try { s.getBasicRemote().sendText(message); } catch (Exception ignored) { }
        });
    }
}
```

2. 各实例订阅同一个 Redis 频道，收到消息后调 `sendToAllLocalClient`：

```java
@Configuration
public class RedisSubscriberConfig {
    @Bean
    RedisMessageListenerContainer container(RedisConnectionFactory factory, WebSocketServer ws) {
        RedisMessageListenerContainer c = new RedisMessageListenerContainer();
        c.setConnectionFactory(factory);
        c.addMessageListener((message, pattern) ->
            ws.sendToAllLocalClient(new String(message.getBody(), StandardCharsets.UTF_8)),
            new ChannelTopic("ysd:ws:broadcast"));
        return c;
    }
}
```

3. 业务方（order-service）不再直接 `webSocketServer.sendToAllClient()`，改为发 Redis：

```java
// OrderServiceImpl.paySuccess / reminder
Map<String, Object> msg = new HashMap<>();
msg.put("type", 1);                          // 1 来单提醒 2 客户催单
msg.put("orderId", ordersDB.getId());
msg.put("content", "订单号：" + outTradeNo);
redisTemplate.convertAndSend("ysd:ws:broadcast", JSON.toJSONString(msg));
```

4. **网关必须支持 WebSocket 升级**：

```yaml
- id: push-service
  uri: lb:ws://ysd-push-service
  predicates:
    - Path=/ws/**
```

> 备选方案：STOMP + `RabbitMQ`/`Redis` 的 `SimpleBroker`，或在网关层直接做 WebSocket 代理。但前端（小程序/管理端）当前用的是原生 WebSocket 且不涉及定向推送（只群发），Pub/Sub 方案改动最小。

### 4.8 共享 POJO 与循环依赖（C16/C17）

- `ysd-pojo` **不要被所有服务依赖**。改造为：
  - 各服务保留**自己内部的** `entity`/`mapper`/`dto`/`vo`（放在自己模块里）；
  - 新增 `ysd-api` 只放**跨服务契约**（Feign 接口 + 瘦 DTO）；
  - `ysd-common` 只留真正通用的东西：`Result`/`PageResult`/`BaseException`/各类业务异常/`BaseContext`/`JwtUtil`/`JacksonObjectMapper`/常量。**移除** `AliOssUtil`（归 file-service）、`WeChatPayUtil`（归 pay-service）、`properties/*`（归各服务自己）。
- `allow-circular-references: true`（`application.yml:8`）应删除。拆服务后一旦出现循环调用（如 order → user → order），会变成分布式死锁，必须用事件驱动解开。

### 4.9 报表与工作台（C7，最难的一条）

`ReportServiceImpl` 与 `WorkspaceServiceImpl` 直接聚合 `orders`/`user`/`drug`/`drug_combo` 四张表（`sumByMap`、`countByMap`、`getSalesTop10`）。拆服务后：

| 方案 | 做法 | 评价 |
|---|---|---|
| **① 报表独立库 + 事件同步（推荐）** | `ysd-report-service` 连一个只读库/从库，通过 MQ 消费订单/用户变更事件写入 `report_daily_order` 等宽表，报表只查自己的宽表 | 性能最好，可水平扩展，彻底解耦。改造量大 |
| ② Feign 聚合 | `report-service` 调 `orderClient.statistics()` / `userClient.statistics()` | 改动小，但跨服务聚合慢、N+1、且报表日期范围大时内存爆 |
| ③ 报表直接读业务库 | 保留原 SQL，连 `sky_order`/`sky_user` 库 | **反模式**（共享数据库），但作为**过渡期方案**可接受，建议加只读账号 + 从库 |

**推荐路径**：一阶段先用 ③（保持原代码，只改数据源），二阶段迁到 ①。`ReportController` 的 Excel 导出（POI）留在 report-service 内，不拆。

### 4.10 营业状态与店铺（C15）

`SHOP_STATUS` 目前 admin 写、user 读，共用 Redis key。改造后：

- **保留共享 Redis**（Redis 本就是基础设施，不算服务耦合），key 统一为 `ysd:shop:status`；
- 归属 `ysd-admin-service` 管理（写），其他服务读；
- 或者更彻底：新建 `ysd-shop-service`。**不建议**——一个 int 状态不值得一个服务。

### 4.11 支付与回调（原有缺陷 2）

- 抽 `ysd-pay-service`，或并入 `ysd-admin-service`。
- `notifyURL` / `refundNotifyUrl`（`application-dev.yml:22,23`）当前指向 cpolar 隧道，集群化后必须指向**网关固定域名**，再由网关路由到 pay-service，否则多实例下回调落到错误实例。
- **支付成功必须走 MQ**，不要像现在这样直接改库：

```
微信回调 → gateway /notify/paySuccess → pay-service
         → 发 MQ 事件 OrderPaidEvent(orderNumber, transactionId)
         → order-service 消费：改订单状态 + 发 Redis 广播（来单提醒）
```

同时 `OrderController` 里的 `paySuccess` 轮询接口需要改为查询订单真实状态，而不是像 `payment()`（`OrderServiceImpl.java:145`）那样硬编码成功。

| 风险 | 影响 | 缓解 |
|---|---|---|
| 版本不匹配（Boot 3.5.16 vs SC 2025.0.x / SCA 2025.0.0.0）| 启动失败/Bean 冲突 | 严格按第二章版本表；先建空工程验证再迁移；SC/SCA 版本以官方 release train 说明为准 |
| 目标 SC/SCA 版本更迭 | 需与 Boot 3.x 对齐（`jakarta.*` 改造已于 2026-09-29 完成） | 已不再是阻碍；按第二章版本矩阵核对后即可落地 |
| 拆 Catalog 导致 JOIN 崩盘 | 分页、排序、删除校验全部失效 | **方案 A 不拆 Catalog** |
| 分布式事务引入 Seata 复杂度过高 | 全局锁、脏回滚、运维成本 | 只对真正需要的写用 Seata，优先 MQ 最终一致 |
| Feign 循环调用 | 分布式死锁 | 内部接口按调用方向单向设计；用事件替代双向调用 |
| ThreadLocal 身份丢失 | 越权/取不到 userId | 网关透传 + Feign 拦截器 + 下游还原，**三处都必须做** |
| 多实例定时任务重复执行 | 重复处理、重复退款 | ShedLock / Redisson |
| WebSocket 推送丢失 | 商家收不到来单提醒 | Redis Pub/Sub + 独立 push-service |
| 报表跨库聚合性能崩 | 报表超时 | 一阶段读从库，二阶段 CQRS 宽表 |
| 改造期间业务不可用 | 影响交付 | 绞杀者模式逐模块切换，网关路由可秒级回滚 |

**回退策略**：每个阶段都保留 `ysd-server` 全量可运行版本（打 tag），网关路由配置支持按路径切回 `ysd-server`。任何阶段出问题，改一条路由即可回退，无需回滚数据。

## 八、不建议做的事（避免过度设计）

1. **不要把 11 张表拆成 11 个服务**。Database-per-service 不等于 Table-per-service。
2. **不要拆分类/药品/药品组合**。三者共享 JOIN 与引用校验，属同一限界上下文。
3. **不要拆购物车**。它与订单的写入路径深度耦合（C1/C4/C6）。
4. **不要用 Seata 处理所有事务**。能本地事务的绝不跨服务，能最终一致的绝不强一致。
5. **不要引入消息队列来做同步查询**。Feign 够用就别上 MQ。
6. **不要一开始就上 K8s + 服务网格**。先把注册中心/网关/Feign 跑通。
7. **不要为了微服务而保留 `ysd-pojo` 共享模块**。这是共享领域模型反模式的入口。
8. **不要跳过观测性改造**。没有链路追踪的微服务排障成本极高。

## 九、改造优先级速查表

| 优先级 | 事项 | 理由 |
|---|---|---|

| P2 | 抽 catalog 服务（含字段冗余） | 承载主要业务 |

| P3 | 报表 CQRS 宽表 | 可长期用「读从库」过渡 |
