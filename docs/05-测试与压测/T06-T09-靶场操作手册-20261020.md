### 1.4 明天怎么看 Druid 面板

1. 打开 <http://localhost:8085/druid/login.html>，登录 `admin / admin`。
2. 点顶部 **数据源**（或直接访问 `/druid/datasource.html`）。
3. 重点看这几列：

| 指标 | 含义 | 判读 |
|---|---|---|
| `MaxActive` | 池上限 | 应为 5 |
| `ActiveCount` | 当前被借出的连接 | 长时间贴在 5 = 池子被打满 |
| `PoolingCount` | 池内空闲连接 | 掉到 0 = 没有可用连接 |
| `WaitThreadCount` | 正在排队等连接的线程 | **持续上升**是最直观的“排队”证据 |
| `NotEmptyWaitCount` | 累计等待次数 | 压测期间快速增长 |
| `NotEmptyWaitMillis` | 累计等待耗时 | 与 WaitThreadCount 一起看 |

判读口径：

- `ActiveCount ≈ 5` 且 `WaitThreadCount` 持续 > 0 → **连接池饱和，线程在排队**。
- `max-wait=5000`，排队超过 5 秒的请求会抛 `GetConnectionTimeoutException`，JMeter 里表现为 500 / 错误率上升。
- 停止施压后，`ActiveCount` 应回落、`WaitThreadCount` 应归零；若不回落，才怀疑连接泄漏。

辅助证据：

```sql
-- DB 侧总连接（在 MySQL 里执行）
SHOW STATUS LIKE 'Threads_connected';
SHOW FULL PROCESSLIST;
```

```bash
# 看线程是否卡在拿连接（PowerShell / Git Bash 均可，PID 换成当前值）
jstack 12688 | grep -A 20 "DruidDataSource.getConnection"
```

Druid 的 `SQL 监控` 页还能看到 `historyOrders` 对应的 SQL 执行次数与耗时，便于区分“池太小”还是“SQL 慢”。

## 2. P2 · T08 事务锁等待与死锁

### 2.1 选用的真实数据

- 订单 1：`orders.id = 6`（status = 3）
- 订单 2：`orders.id = 7`（status = 6）

脚本（复制即用）：

- `docs/05-测试与压测/靶场脚本/t08-deadlock-session-a.sql`
- `docs/05-测试与压测/靶场脚本/t08-deadlock-session-b.sql`
- `docs/05-测试与压测/靶场脚本/t08-deadlock-check.sql`

### 2.2 复现步骤（两个独立 MySQL 会话）

开两个客户端窗口（推荐两个终端）：

```bash
docker exec -it Study mysql -uroot -proot ysd_take_out
```

严格按顺序：

| 步骤 | 会话 A | 会话 B |
|---|---|---|
| 1 | `START TRANSACTION;` | |
| 2 | `SELECT id,status FROM orders WHERE id=6 FOR UPDATE;` | |
| 3 | | `START TRANSACTION;` |
| 4 | | `SELECT id,status FROM orders WHERE id=7 FOR UPDATE;` |
| 5 | `SELECT id,status FROM orders WHERE id=7 FOR UPDATE;` → **阻塞** | |
| 6 | | `SELECT id,status FROM orders WHERE id=6 FOR UPDATE;` → **死锁** |

预期：

- 会话 B 报错：
  `ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction`
- 会话 A 解除阻塞，拿到 id=7。
- InnoDB 会自动回滚其中一个事务（本次实测回滚的是 B）。

> 用的是 `SELECT ... FOR UPDATE`，只加锁、不改数据；死锁/等待结束后 `ROLLBACK` 即可。

### 2.3 观测与解锁

```sql
SHOW ENGINE INNODB STATUS\G
-- 找 LATEST DETECTED DEADLOCK 段：
--   *** (1) TRANSACTION / *** (1) HOLDS THE LOCK(S) / WAITING FOR THIS LOCK
--   *** WE ROLL BACK TRANSACTION (x)
```

MySQL 8 还可以看：

```sql
SELECT * FROM performance_schema.data_lock_waits;
SELECT * FROM performance_schema.data_locks;
SHOW FULL PROCESSLIST;
```

收尾（两个窗口都执行）：

```sql
ROLLBACK;
```

确认没有残留事务：

```sql
SELECT trx_id, trx_state, trx_mysql_thread_id, trx_query
FROM information_schema.innodb_trx;
-- 正常应为空
```

今晚已实测证据：
- `docs/05-测试与压测/evidence/T08-session-b-20261020.log`（`ERROR 1213`）
- `docs/05-测试与压测/evidence/T08-innodb-status-20261020.txt`（`LATEST DETECTED DEADLOCK` 全文）

## 6. 两个必须知道的坑

1. **Windows 文件锁**：服务运行时 jar 被占用，`mvn package` 会在 `spring-boot:repackage` 阶段报 “Unable to rename ...jar”。**先停服务再打包**。
2. **必须 `-am` + `clean`**：只打 `ysd-order-service` 会从本地仓库取旧 `ysd-pojo`（今晚就踩到了 `comboId` getter 缺失）。命令固定用：
   `mvn -pl ysd-order-service -am -DskipTests clean package`
