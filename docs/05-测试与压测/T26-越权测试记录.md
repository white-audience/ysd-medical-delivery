## 1. 漏洞原理

**水平越权（IDOR）**：服务端直接使用客户端传入的对象标识（如 `addressBookId`）查询数据，却没有校验该对象是否属于当前登录用户。攻击者只要把 id 改成其他用户的对象 id，就能读写他人的数据。它与“垂直越权”（普通用户访问管理员功能）相对，发生在**同一权限级别的用户之间**。

本项目的触发点：

1. 用户提交订单：`POST /user/order/submit`，Body 中携带 `addressBookId`。
2. `OrderServiceImpl.submitOrder` 直接把它传给 Feign：
   `userClient.getAddressBookById(ordersSubmitDTO.getAddressBookId())`
   （`ysd-order-service/src/main/java/com/ysd/service/impl/OrderServiceImpl.java:74`）
3. user-service 内网接口 `InnerAddressBookController#getById` 只按主键查询：
   `addressBookService.getById(id)` → SQL `select * from address_book where id = #{id}`。
4. 查询结果虽然只返回 `consignee` / `phone` 两个字段，但足以让 User B 用 User A 的收货信息生成自己的订单，造成 PII 泄露与订单归属混乱。

关键点：身份其实已经可用——网关校验 JWT 后注入 `X-Identity-Id`，Feign 出站拦截器会把 `BaseContext` 中的 userId 继续透传。但内网查询接口**完全没有使用这个可信身份**。

## 2. 复现步骤（修复前）

### 2.1 环境与数据

- 本地全链路：gateway `:9000`、user-service `:8081`、order-service `:8085`
- User A：`user_id=4`，`address_book.id=2`（`lisally / 13212345678`）
- User B：`user_id=5`，无地址簿数据
- 两个用户各用测试密钥签发 JWT（`python jmeter/gen-user-token.py 4|5`）

### 2.2 攻击请求

User B 的 Token + User A 的地址 id：

```http
POST http://127.0.0.1:9000/user/order/submit
Content-Type: application/json
authentication: <JWT userId=5>

{"addressBookId":2,"payMethod":1,"remark":"T26-IDOR-test","deliveryStatus":1,
 "tablewareNumber":0,"tablewareStatus":1,"packAmount":0,"amount":6.00}
```

### 2.3 攻击结果

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"code":1,"msg":null,"data":{"id":40,"orderNumber":"1792580467026","orderAmount":6.00,"orderTime":"2026-10-21 19:01"}}
```

数据库 `orders` 表：

| id | user_id | consignee | phone | amount | remark |
|----|---------|-----------|-------|--------|--------|
| 40 | **5** | **lisally** | **13212345678** | 6.00 | T26-IDOR-test |

订单归属 User B，收货信息却来自 User A 的地址簿，**越权复现成功**。

### 2.4 根因直证

绕过 order-service，直接请求内网接口（模拟 Feign 调用）：

```http
GET http://127.0.0.1:8081/inner/addressBook/2
X-Identity-Id: 5

HTTP/1.1 200
{"code":1,"msg":null,"data":{"consignee":"lisally","phone":"13212345678"}}
```

身份头为 5，仍返回 `user_id=4` 的地址，证明接口未做归属校验。

## 3. 修复方案

### 3.1 改动点

| 文件 | 改动 |
|------|------|
| `ysd-user-service/.../mapper/AddressBookMapper.java:36-40` | 新增 `getByIdAndUserId`，SQL 为 `where id = #{id} and user_id = #{userId}` |
| `ysd-user-service/.../service/AddressBookService.java` | 新增对应接口方法 |
| `ysd-user-service/.../service/impl/AddressBookServiceImpl.java:54-56` | 实现联合查询 |
| `ysd-user-service/.../controller/inner/InnerAddressBookController.java:28-37` | userId 取自 `BaseContext`，按 `id + userId` 查询；查不到返回“地址不存在或无权限” |
| `ysd-common/.../constant/MessageConstant.java:18` | 新增错误提示常量 |

核心代码：

```java
Long userId = BaseContext.getCurrentId();
if (userId == null) {
    return Result.error(MessageConstant.USER_NOT_LOGIN);
}
AddressBook addressBook = addressBookService.getByIdAndUserId(id, userId);
if (addressBook == null) {
    return Result.error(MessageConstant.ADDRESS_BOOK_NOT_EXIST_OR_DENIED);
}
```

order-service 无需改动：`unwrap()` 遇到 `code != 1` 会抛出业务异常，整个下单事务回滚，不会写订单与订单明细，也不会清空购物车。

### 3.2 为什么 userId 从 Feign Header 取，而不是请求参数

调用链上的身份来源是可信的：

1. **网关**解析用户 JWT，取出 `userId` 后写入 `X-Identity-Id`；同时在入口处先删除客户端自带的同名头，防止伪造（`AuthGlobalFilter.java:51-56`）。
2. **order-service** 的 `JwtTokenUserInterceptor` 把该头写入 `BaseContext`。
3. **Feign 出站拦截器** `FeignRequestInterceptor` 从 `BaseContext` 取出 userId，继续写入下游请求头。
4. **user-service** 的 `InnerIdentityInterceptor` 读取该头，写入 `BaseContext`，控制器从这里取值。

因此 `BaseContext.getCurrentId()` 是“网关已认证身份”的延续。反之，如果把 userId 放在 Body 或 Query 中，攻击者可以随意填写，等于把越权校验交给前端，无法防御 IDOR。

另外，`/inner/**` 由网关统一 403，不对外暴露，外部无法直接伪造该头。

### 3.3 失败语义

查不到归属时返回业务错误“地址不存在或无权限”，而不是空数据。这样既符合预期，也避免通过不同响应区分“地址不存在”和“地址存在但不属于你”（减少枚举信息）。order-service 最终返回：

```json
{"code":0,"msg":"查询地址簿失败：地址不存在或无权限","data":null}
```

## 4. 回归结果

| 场景 | 修复前 | 修复后 |
|------|--------|--------|
| User B 传 User A 的 `addressBookId=2` 下单 | 200，成功生成订单 40 | `code=0`，地址不存在或无权限；订单数不变 |
| User B 直接调用内网 `/inner/addressBook/2` | 返回 A 的收货人/电话 | `code=0`，地址不存在或无权限 |
| User A 传自己的 `addressBookId=2` 下单 | 成功 | 成功，生成订单 41，行为一致 |
| User B 的购物车 | 被清空 | 失败时不执行后续逻辑，购物车保留 |

回归细节：

- User B 失败后 `orders` 总数保持 23，未新增订单；购物车条目仍在。
- User A 成功后 `orders` 总数 24，订单 41 的 `user_id=4`、收货信息正确，购物车正常清空。
- 说明修复没有破坏正常下单流程，`@Transactional` 回滚行为符合预期。

## 5. 残留风险与后续建议（不在 T26 范围）

1. **C 端地址簿接口同样缺少归属校验**：`/user/addressBook/{id}` 的查询、`PUT /user/addressBook` 修改、`DELETE /user/addressBook` 删除都只按 id 操作。任意登录用户可读取、修改、删除他人地址，属于同一类 IDOR。建议单独建任务（T27），统一改为 `id + BaseContext.getCurrentId()` 操作，并在 SQL 层加 `user_id` 条件。
2. **BaseContext 未在线程复用前清理**：现有拦截器只 `set` 不 `remove`。虽然当前内网调用都会带身份头，但建议在拦截器 `afterCompletion` 中调用 `BaseContext.removeCurrentId()`，避免线程池复用导致身份串号。
3. 测试 Token 使用本地默认密钥签发，仅用于开发环境；生产环境必须使用独立强密钥并缩短有效期。
