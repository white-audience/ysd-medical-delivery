## 二、第一组：把 JMeter 性能测试做完整

你现有的 50 线程、固定循环测试适合验证功能，但还不足以确定系统容量。建议把下面几种测试补进去。

### 1. 基准测试：先知道系统正常时是什么水平

选取几个有代表性的接口：

| 接口                                 | 主要观察点             |
| ---------------------------------- | ----------------- |
| `GET /user/drug/list?categoryId=1` | 缓存命中、数据库查询、序列化    |
| `POST /user/shoppingCart/add`      | 数据库写入、Feign、购物车并发 |
| 订单创建接口（以实际路由为准）                    | 事务、库存、订单正确性       |
| 管理端药品更新接口                          | 写入耗时、缓存失效、并发读写    |

每个接口分别测：

- 低并发：1～5 个线程，建立响应时间基线。
- 中等并发：逐步增加线程，观察性能变化。
- 稳定并发：保持固定负载，观察 P50、P95、P99 和错误率。
- 缓存命中和缓存未命中：分别测试，不能混在一起比较。

先别把 P95 小于 50ms 当作硬性标准。 你现有文档中的这个数字可以作为本机缓存命中场景的参考目标，但不是所有接口、所有机器都应该满足的生产标准。

你需要记录一份自己的基线：

| 指标    | 记录内容                |
| ----- | ------------------- |
| 吞吐量   | 稳定运行时每秒成功请求数        |
| 响应时间  | P50、P95、P99、最大值     |

不要只测试一次 50 线程。建议在隔离测试环境中依次运行：

| 阶段 | 并发设置示例 | 目的          |
| -- | ------ | ----------- |
| A  | 5      | 建立轻负载基线     |
| B  | 10     | 观察初步增长      |
| C  | 20     | 检查资源变化      |
| D  | 40     | 观察延迟是否加速增长  |
| E  | 60     | 探索性能拐点      |
| F  | 80     | 仅在前面阶段稳定时继续 |

每个阶段运行 2～5 分钟，逐渐增加负载；如果错误率持续升高、P99 急剧恶化或资源接近上限，就停止继续加压。

这里的数字只是测试阶梯，不是你的项目应该达到的并发标准。具体还取决于电脑性能、数据库配置、请求复杂度和 JMeter 施压能力。

你要寻找的不是最大 TPS，而是性能拐点。

例如：

- 20 并发时 P95 为 80ms。
- 40 并发时 P95 为 120ms。
- 60 并发时 P95 突然上升到 900ms。
- 同时 MySQL 活跃连接数接近连接池上限。

这时就应该调查连接池、SQL 和数据库负载，而不是继续增加线程，试图把 TPS 压上去。

### 3. 突发流量测试：模拟突然涌入的请求

正常的阶梯加压无法完全模拟促销活动、客户端重试或流量突然集中到来的情况。

建议使用 JMeter 的 Synchronizing Timer、定时器和多个线程组，模拟：

1. 低负载运行 2 分钟。
2. 短时间内让大量线程同时发请求。
3. 突发结束后恢复低负载。
4. 观察系统多久恢复到原来的响应时间。

重点看：

- 网关是否按预期限流。
- 是否出现大量 502、503、429 或超时。
- MySQL 连接池是否被占满。
- Redis 是否突然出现大量 miss。
- RabbitMQ 是否出现消息堆积。
- 流量下降后，服务是否仍然很慢。

真实问题往往发生在突发流量结束以后。 因为请求积压、线程阻塞、数据库连接尚未释放，系统可能不会立即恢复。

### 4. 长时间稳定性测试：检查慢性问题

建议先连续运行 30～60 分钟，稳定后再尝试 2～4 小时。没有必要一开始就跑一整天。

重点观察：

- JVM 老年代使用量是否持续增长。
- GC 暂停是否逐渐变长。
- 活跃线程是否不断增加。
- 数据库连接是否泄漏。
- Redis 连接是否耗尽。
- 日志文件是否快速增长并占满磁盘。
- MQ 消费速度是否低于生产速度。
- P95/P99 是否随运行时间逐步恶化。

如果刚开始性能正常，20 分钟后越来越慢，就要怀疑连接泄漏、内存泄漏、任务堆积、慢查询积累等问题。

### 5. JMeter 自身也可能成为瓶颈

这是一个很容易误判的地方。

如果 JMeter 所在电脑的 CPU 已经很高，或者施压线程不足，那么测试结果可能只是测试机的极限，而不是服务端的极限。

建议：

- 使用非 GUI 模式执行正式压测。
- 不要在高并发时打开 `View Results Tree`。
- 使用 Aggregate Report、Backend Listener 或结果文件记录数据。
- 同时监控 JMeter 客户端 CPU、内存和网络。
- 先确认施压端能稳定产生预期的请求速率。

你现有指南已经提醒不要在高并发测试中使用 `View Results Tree`，这条应该保留。

## 三、第二组：数据库问题——最值得提前练习的线上排障场景

你目前的压测计划比较关注 Redis 和 Sentinel，但真实的 Spring Boot / Spring Cloud 服务中，MySQL 连接池、慢 SQL 和事务锁等待，往往是非常值得重点练习的排障方向。

### 测试 6：数据库连接池耗尽

模拟场景： 请求量增加后，接口越来越慢，最终大量请求超时，但 CPU 可能并不高。

常见原因：

- 数据库连接池设置过小。
- SQL 执行时间太长，连接迟迟不能归还。
- 事务持有连接的时间过长。
- 某段代码获取连接后没有正常释放。
- 多个服务共享同一个数据库，连接数总量超出数据库承受能力。

怎么测？

1. 记录各服务的数据源连接池配置，确认最大连接数、获取连接超时和连接等待时间。
2. 通过 JMeter 对购物车、订单等数据库读写接口逐步加压。
3. 观察连接池的 active、idle、pending 和获取连接耗时。
4. 同时检查 MySQL 当前连接数和慢查询。
5. 在测试环境中适当调低连接池上限，复现连接等待，完成后恢复配置。

如果项目使用 HikariCP，可以重点观察连接池的 Active、Idle、Pending、Max 等指标；具体指标名称取决于你是否暴露了 Spring Boot Actuator / Micrometer。

出现问题后怎么定位？

| 现象                           | 优先怀疑                  |
| ---------------------------- | --------------------- |
| Active 长期等于 Max，Pending 持续增加 | 连接池饱和或连接被长时间占用        |
| Active 很高，MySQL 查询也很慢        | SQL、锁等待、数据库资源瓶颈       |
| Active 很高，但数据库负载不高           | 事务过长、连接使用不当、慢网络或连接泄漏  |
| 调大连接池后数据库更慢                  | 数据库并发能力不足，连接数增加反而加重争用 |

修复不能只停留在调大连接池。你需要进一步找到连接被占用的原因，再验证 P95、Pending 和数据库负载是否改善。

### 测试 7：慢 SQL 和索引失效

建议你专门准备一个可重复的实验。

在测试数据库里准备足够多的数据，例如 10 万条以上的订单或药品关联数据。数据量较小的本地数据库，很难体现某些索引和执行计划问题。

测试步骤：

1. 找到一个真实业务查询，例如订单列表或按条件查询药品。
2. 使用 `EXPLAIN` 查看执行计划。
3. 记录查询耗时、扫描行数和返回行数。
4. 尝试在测试环境中去掉或调整索引，比较执行计划和耗时。
5. 恢复合适的索引后再次测试。
6. 检查新增索引对写入性能和存储空间的影响。

常用命令：

```
EXPLAIN
SELECT *
FROM orders
WHERE user_id = 10001
ORDER BY order_time DESC
LIMIT 20;
```

表名和字段需要按你项目真实的 MySQL 结构调整。

注意：不要只看 `type` 是否为 `ALL` 就认定查询一定有问题，也不要认为添加索引必然更快。需要结合过滤比例、扫描行数、排序、表规模及实际耗时综合判断。

建议额外练习三种查询：

- 深分页：`LIMIT 100000, 20` 与基于游标或最后一条记录的分页方式比较。
- 低选择性条件：例如大量记录都具有相同状态时，评估索引是否有收益。
- N+1 查询：一次查询订单，再循环查询订单明细或关联信息，观察 SQL 数量随数据量增长的变化。

这三个场景比单纯背诵索引原理更有助于你实际定位问题。

### 测试 8：事务锁等待与死锁

模拟两个并发事务争抢相同的业务数据，例如同一个药品库存、同一个订单或同一个购物车记录。

先在测试数据库中用两个数据库会话验证基本现象：

```
-- 会话 A
START TRANSACTION;
UPDATE inventory
SET stock = stock - 1
WHERE product_id = 1001;

-- 暂时不要提交
```

```
-- 会话 B
UPDATE inventory
SET stock = stock - 1
WHERE product_id = 1001;
```

这里是示意 SQL，表名、字段和约束必须按实际结构调整。会话 B 可能等待会话 A 释放锁。

再通过 JMeter 对实际业务接口施加并发，观察请求耗时和数据库锁等待。

排查时可以检查：

```
SHOW FULL PROCESSLIST;
SHOW ENGINE INNODB STATUS;
```

在 MySQL 8 中，还可以检查 `performance_schema` 下的锁等待相关视图。

你需要区分：

- 锁等待：事务持有锁的时间较长，其他事务被阻塞。
- 死锁：事务之间形成循环等待，InnoDB 通常会选择一个事务回滚。
- 业务竞争：数据库没有报错，但两个请求基于相同的旧库存做出错误决策。

修复时要考虑缩短事务、统一加锁顺序、合适的索引和重试机制。死锁重试必须限制次数，并确保重试不会导致重复扣库存或重复创建订单。

不要在生产数据库里为了练习随意持有事务不提交；这会阻塞真实业务。

### 测试 9：事务回滚与部分失败

这是非常实用、但容易被忽略的测试。

假设创建订单需要：

1. 扣减库存。
2. 创建订单主表记录。
3. 写入订单明细。
4. 发送订单创建消息。

在测试环境中人为让第 3 步失败，检查前两步是否正确回滚。

再检查消息是否可能在数据库事务最终失败时仍然发送出去。

你需要验证的不是接口返回了错误，而是：

- 库存有没有被扣减。
- 订单主表有没有残留记录。
- 订单明细是否完整。
- MQ 是否存在错误的订单创建消息。
- 重试请求是否会重复创建订单。

如果订单与库存分别位于不同服务，就不能默认一个本地 `@Transactional` 可以同时回滚两个服务的数据。此时要考虑服务间一致性、幂等、补偿或事务消息等方案。

## 四、第三组：Redis 缓存——从“缓存有效”升级到“缓存故障”

你现在已经有缓存命中、空值缓存、延迟双删测试。这些是很好的起点，但建议继续验证下面几种场景。

### 测试 10：缓存击穿与热点 Key 失效

缓存穿透是访问不存在的数据；缓存击穿则是大量请求同时访问一个存在、但刚好失效的热点数据。两者不能混为一谈。

复现方法：

1. 选取一个热门药品分类。
2. 先预热缓存。
3. 让这个 Key 到期，或者只在测试环境删除该 Key。
4. 同时用多个线程请求同一分类。
5. 观察 MySQL 查询次数和接口 P99。

重点判断：多个并发请求同时发现缓存不存在时，是否都打到数据库？

你目前的实现涉及缓存加载锁，所以要确认锁是否真的把回源请求合并起来，而不是仅仅让每个请求轮流查询数据库。

### 测试 11：缓存雪崩与 TTL 集中到期

你现有药品缓存使用带随机抖动的 TTL，这有助于避免一批缓存同时过期。

jmeter-test-plan.md



但还需要验证这种设计在高负载下是否有效。

实验：

- 准备一批热点 Key。
- 在隔离环境中构造一批过期时间接近的缓存。
- 对这些 Key 对应的接口同时施压。
- 观察 Redis miss、MySQL QPS、连接池和接口延迟。
- 再对比随机 TTL、缓存预热或限流等方案。

如果数据库突然承受大量回源查询，就要考虑缓存过期策略、热点数据预热、请求合并以及必要的数据库保护措施。

注意：Redis 业务库是 db10，不要为了实验执行 `FLUSHDB` 或 `FLUSHALL`。优先使用明确的测试 Key 前缀和独立测试环境。

### 测试 12：Redis 不可用时，系统会怎样？

建议分别测试三种故障：

- Redis 服务停止。
- Redis 网络延迟或连接建立超时。
- Redis 恢复后，缓存全部为空。

重点关注你的缓存辅助类是怎么处理 Redis 异常的。

如果缓存读取失败后直接查数据库，可能出现以下链式故障：

Redis 不可用 → 缓存失效 → 大量请求回源 → MySQL 连接池耗尽 → 所有业务接口超时。

这种情况叫作故障放大。

你要验证：

1. Redis 连接失败是否会导致请求一直等待。
2. 缓存异常时是否有合理的超时和降级。
3. MySQL 是否能承受有限时间内的回源压力。
4. Redis 恢复后，缓存是否逐步重建。
5. 缓存恢复期间，其他服务是否受到明显影响。

这里不能简单地规定“Redis 挂了就必须查数据库”。对高流量系统来说，无限制回源可能比直接失败更危险，需要根据接口的重要程度决定限流、返回错误或受控回源。

### 测试 13：延迟双删在多实例下是否仍然正确

你当前文档已经明确指出，本地锁和延时任务仅在单实例范围内有效，多实例情况下存在局限。

jmeter-test-plan.md



这是一个很值得深入的测试，因为它涉及微服务部署方式与数据一致性。

实验方案：

1. 启动两个 catalog-service 实例。
2. 对同一个药品进行高频读写。
3. 让一个实例执行更新，另一个实例同时读取。
4. 检查两实例是否出现不一致的缓存状态。
5. 检查延迟删除任务是否可能失败、延迟或没有被执行。
6. 写入后等待超过设计的延迟窗口，再核对数据库与缓存。

如果发现多实例下缓存仍然可能出现旧值，需要考虑分布式失效通知、可靠的延时消息或其他一致性设计。

还有一个边界要特别注意：延迟双删并不等于严格强一致性。 即使延时删除执行成功，也不能仅凭一次测试就证明任意并发顺序下永远不会出现旧值。应该通过多轮并发测试、故障注入和明确的一致性目标来评估。

## 五、第四组：RabbitMQ——真正的线上问题经常出现在消息链路

你的项目中有 `order-service` 和 `push-service`，通过 MQ 消费实现推送相关处理。现有测试也提到了订单服务到推送服务的 Trace 验证。

jmeter-test-plan.md



这意味着你应该把消息队列当作一条独立的故障链路来测试，而不只是确认消息能正常发送。

### 测试 14：消费者停止，消息会不会堆积？

[Query messages--Message Queue for RabbitMQ-Byteplus](https://images.openai.com/static-rsc-4/iEM9A1Fru4htNsaYd37f70SiVsoczYxo-VDL7cod0IVZwtLLiqQJuirhVzuh_Eh1jonQmInfqfSvoi44tE0T7kqD588eC3DL29qxK-jsK50D55ZQJ-JTe6shrqdWNw_8isBtAKg_yr1DvCKE9CzHMXNf45R62NGsU3sdWDI3H6A?purpose=inline)

[docs.byteplus.com](https://docs.byteplus.com/api/docs/rabbitmq/Query_messages)

测试步骤：

1. 记录 RabbitMQ 队列的初始 Ready、Unacked 数量。
2. 在测试环境停止 `push-service` 消费者。
3. 通过 JMeter 对实际会发送消息的业务接口持续施压。
4. 观察队列长度是否增加。
5. 恢复 `push-service`。
6. 观察积压消息是否逐步被消费，最终回到正常水平。

你要记录的指标：

- 消息生产速率。
- 消息消费速率。
- Ready 消息数。
- Unacked 消息数。
- 消费失败与重试次数。
- 消息从产生到处理完成的延迟。

如果生产速度长期大于消费速度，队列就会不断增长。

可以用一个简单的估算帮助理解：假设每秒产生 200 条消息，消费者每秒处理 150 条，队列每秒净增加约 50 条。如果这种差距持续存在，单纯重启消费者并不能根治问题。

### 测试 15：消息重复消费

这是比单纯检查 MQ 有没有消息更重要的测试。

模拟以下情况：

1. 消费者收到一条消息。
2. 消费者完成业务数据库操作。
3. 在消息成功确认前，主动让消费者异常退出。
4. 恢复消费者，观察该消息是否再次投递。

如果消息可能被重复消费，就必须检查业务是否具备幂等性。

例如订单状态更新、库存扣减、积分发放等操作，不应该因为同一条消息被处理两次就执行两遍。

建议测试：

- 同一消息连续投递两次。
- 同一消息在两个消费者实例中竞争处理。
- 消费者处理成功但确认失败。
- 消费者处理失败后重新投递。

修复思路包括业务唯一键、消费记录表、状态条件更新以及合理的重试策略。需要注意，单独增加一个“已处理”标记，如果它与业务操作不在同一个可靠的事务边界内，也可能留下重复处理的窗口。

### 测试 16：消息发送成功，但业务数据没有正确提交

假设订单服务写入订单后发送 MQ 消息。如果消息发送与数据库事务不是一个可靠的一致性方案，就可能出现：

- 数据库回滚了，但消息已经发送。
- 数据库提交成功，但消息发送失败。
- 服务在数据库提交和消息发送之间崩溃。

你可以通过在测试环境里人为制造失败，检查数据库和队列最终是否一致。

如果目前使用普通的数据库事务加消息发送，不要直接认为两者天然具备原子性。根据一致性要求，可以研究事务消息、Transactional Outbox（事务发件箱）、可靠重试和补偿机制。

### 测试 17：消息顺序、死信与毒消息

继续测试：

- 同一订单连续发送“创建、支付、取消”消息时，消费者是否可能乱序处理。
- 一条始终处理失败的消息是否会无限重试。
- 消息进入死信队列后有没有监控和处理流程。
- RabbitMQ 短暂不可用时，生产者是否能恢复发送。
- 消息堆积清空后，业务状态是否正确。

注意，RabbitMQ 不同队列类型、消费者数量、预取数量和重试配置，会影响消息顺序及重新投递行为。不能只靠一次测试就假定所有消息都按全局顺序消费。

## 六、第五组：Spring Cloud 微服务故障测试

你的现有方案已经测试了 catalog-service 故障时，order-service 通过 Feign 调用触发熔断降级。

jmeter-test-plan.md



接下来，应该从“一个服务被关闭”扩展为“各种故障发生时，系统的边界是否有效”。

### 测试 18：下游变慢，而不是直接停止

真实生产中，下游服务不一定会直接挂掉。更常见的情况之一是它还活着，但响应变慢。

例如 catalog-service 的某个查询从 50ms 变成 5 秒。

你要测试：

1. 通过测试专用的延迟接口，或者隔离环境的网络延迟注入，让下游响应变慢。
2. 观察 Feign 调用耗时、线程池、连接池和请求排队情况。
3. 验证调用超时和熔断是否按预期工作。
4. 恢复下游后，检查调用链是否自动恢复。

注意：延迟应注入专用测试接口或隔离环境，不要为了制造延迟在共享环境中随意修改真实业务代码。

排查的关键：

如果下游响应慢，上游线程就可能被占用。如果上游又没有合理的超时和并发隔离，就会出现线程堆积，最终导致本来正常的接口也无法响应。

你需要检查：

- Feign 连接超时和读取超时。
- 熔断器的慢调用阈值、滑动窗口和恢复条件。
- 调用是否存在多层重试。
- 请求超时后，后台业务是否仍在执行。
- 下游恢复后，上游是否仍然积压大量等待中的请求。

### 测试 19：服务实例突然退出与重启

不要只测“停止服务后接口报错”，还要测恢复过程。

建议对 catalog-service、order-service 分别执行：

- 正常停止。
- 进程被强制终止。
- 服务重启。
- 启动期间接收请求。
- 多实例中仅一个实例退出。
- 实例重新注册到 Nacos 后继续接收流量。

重点观察：

- Nacos 实例状态和注册信息。
- 网关是否继续将请求路由到失效实例。
- Feign 是否出现额外的重试和延迟。
- 服务启动过程中是否因为数据库、Redis、MQ 尚未就绪而持续报错。
- 恢复后缓存、消费者和定时任务是否正常。

如果停止服务后出现 503，不能直接判定是 Sentinel 问题。也可能是 Nacos 注册状态、网关路由、实例健康状态或调用超时导致的。

### 测试 20：Nacos 暂时不可用

在隔离环境中模拟 Nacos 不可用，分别观察：

1. 已启动的服务是否还能继续处理已有业务请求。
2. 服务重启后能否正常获取必要的配置和注册信息。
3. 配置更新是否会影响运行中的实例。
4. Nacos 恢复后，实例注册、配置同步是否恢复。

这里要区分服务发现故障与配置中心故障，两者表现可能完全不同。

你还需要特别关注 Sentinel 规则是否正常加载。你的指南已经提到，限流和熔断规则保存在 Nacos 中，仓库中的示例阈值并不等于运行时的实际配置。

jmeter-test-plan.md



因此每次做故障实验，都应记录实际加载的规则，而不是仅根据配置文件推断系统行为。

### 测试 21：限流、熔断和重试叠加

这是一个更接近真实线上事故的组合测试。

假设：

- 网关限制某个接口的 QPS。
- order-service 通过 Feign 调用 catalog-service。
- catalog-service 变慢。
- 上游又配置了重试。

你需要确认系统有没有可能因重试放大流量，导致原本只是部分请求变慢，最终演变为全链路拥塞。

建议分别测试：

- 只开启网关限流。
- 只模拟下游变慢。
- 开启熔断。
- 在确认重试配置后测试重试与熔断组合。

观察 429、5xx、超时、调用次数、线程池和数据库连接的变化。

修复思路不是简单地把所有阈值调高，而是让超时、重试次数、熔断策略和并发隔离互相匹配。对非幂等写请求尤其要谨慎重试。

## 七、第六组：业务正确性测试——接口返回成功，不代表系统正确

这部分我建议你优先级放得很高。

JMeter 的聚合报告显示 0% 错误，并不意味着订单、库存和购物车没有问题。因为很多严重的业务 Bug，返回的 HTTP 状态码仍然可能是 200。

### 测试 22：并发扣库存与超卖

假设某个测试商品库存只有 10 件。

用 JMeter 同时发出 50 个购买请求，每个请求尝试购买 1 件。

测试前先明确业务规则：库存不能小于 0，且成功扣减的数量不能超过初始库存。

检查以下结果：

- 最终库存是否小于 0。
- 成功订单数量是否超过 10。
- 是否存在订单创建成功，但库存没有扣减的情况。
- 是否存在库存已经扣减，但订单没有成功创建的情况。
- 是否存在重复请求导致同一用户重复下单。

这里有一个关键区别：接口返回“成功”的次数不等于成功购买的数量。需要根据订单状态、库存记录和业务唯一键来核对。

你可以进一步对比不同实现：

- 先查询库存，再在应用层扣减。
- 使用数据库条件更新，例如 `stock > 0`。
- 使用乐观锁版本号。
- 在适当场景下使用 Redis 原子操作或分布式锁。

不要预设分布式锁一定是最佳方案。数据库条件更新可能更简单可靠；选择哪种实现，要结合库存的权威存储位置、业务事务边界和一致性要求。

### 测试 23：重复提交和幂等性

模拟用户因为页面卡顿或网络超时，连续提交两次相同的下单请求。

需要验证：

- 是否生成两个订单。
- 是否重复扣减库存。
- 是否重复发送消息。
- 客户端超时后再次提交，服务端是否能够识别重复请求。

对于创建订单这类写操作，可以研究幂等键、业务唯一约束和请求状态管理。

注意：简单地禁用前端按钮不能代替后端幂等性。请求可能来自重试、重复消息或其他客户端。

### 测试 24：事务边界和并发更新

建议构造这些场景：

| 场景              | 应验证的结果          |
| --------------- | --------------- |
| 两个用户同时修改同一购物车记录 | 最终数量符合业务规则      |
| 订单更新与取消同时发生     | 状态不能出现非法跳转      |
| 数据库更新成功后缓存删除失败  | 后续有可验证的修复路径     |
| 消费者重复处理订单消息     | 不重复扣减或发放资源      |
| 请求处理中服务崩溃       | 重启后数据状态仍可解释、可恢复 |

这类测试可以结合 JUnit 集成测试、并发测试和 JMeter 完成。并不是所有问题都适合只靠 JMeter 来测；涉及事务精确顺序的情况，最好用程序化并发测试控制执行时序。

### 测试 25：参数异常和边界值

对公开接口和管理端接口补充：

- 必填参数缺失。
- ID 不存在。
- 数量为 0、负数或极大值。
- 超长字符串。
- 非法 JSON。
- 分页参数异常。
- 不支持的状态值。
- 价格精度和金额边界。
- 空数组、重复数组元素。

检查是否出现 500、SQL 异常、未捕获的运行时异常，或者虽然请求失败但已经修改部分数据的情况。

对订单、价格、库存等关键字段，不要只依赖前端校验。服务端应有参数验证、业务规则检查和必要的数据库约束。

## 八、第七组：安全与权限测试

你的项目有 JWT 鉴权，网关也会区分管理端与用户端 token。现有文档已经明确记录了两类请求的 Header 规则。

jmeter-test-plan.md



建议新增下面的验证。

### 测试 26：鉴权边界

分别测试：

- 没有 token。
- token 已过期。
- token 格式错误或签名不正确。
- 管理端 token 访问用户端接口。
- 用户端 token 访问管理端接口。
- 普通用户访问其他用户的数据。
- 伪造身份 Header。
- 直接访问不应暴露的内部接口。

特别注意：鉴权成功不代表权限检查正确。比如用户 A 使用自己的合法 token，访问用户 B 的订单，接口仍然应该拒绝。

这类测试应该以权限规则为基准，而不是只检查是否返回 401。

### 测试 27：异常输入和资源消耗

可以测试过长参数、异常分页、超大请求体、过多筛选条件等情况，确认系统能合理拒绝不合法请求，而不是出现大量内存分配、全表扫描或线程阻塞。

这些测试要设置合理的输入上限，避免在测试环境中制造不必要的资源耗尽。

## 九、第八组：JVM、线程池和操作系统资源

很多线上问题最后表现为“接口越来越慢”，但真正的根因可能不在 SQL 或 Redis，而在 JVM 或服务器资源。

### 测试 28：内存增长与 GC

在持续负载下记录：

- 堆内存使用趋势。
- 老年代占用。
- GC 次数、暂停时间。
- Full GC 是否频繁发生。
- 请求 P99 是否与 GC 暂停同时上升。

如果内存占用持续增长且 GC 后无法回落，就要进一步排查对象保留、缓存无界增长、集合累积和资源未释放等问题。

可使用 JDK 工具辅助分析：

```
jcmd <pid> GC.heap_info
jcmd <pid> Thread.print
jstat -gcutil <pid> 1000
```

以上命令需要在目标 Java 进程所在机器执行，并替换为实际 PID。

不要仅凭一次堆内存较高就认定内存泄漏。应观察多次 GC 后的趋势，再结合堆转储和对象引用分析。

### 测试 29：线程池耗尽

如果业务中存在异步任务、定时任务、消息消费者或自定义线程池，需要检查：

- 线程池活跃线程数。
- 队列长度。
- 拒绝任务次数。
- 任务执行时间。
- 是否出现大量阻塞线程。

例如，某个 Feign 调用持续等待下游响应，可能占用大量业务线程；线程耗尽后，连不依赖这个下游的请求也可能受到影响。

建议把“线程池已满”作为独立的故障场景，而不只是通过接口延迟来间接观察。

### 测试 30：磁盘和日志增长

持续运行服务并观察：

- 日志是否快速增长。
- 是否存在异常重复打印。
- 日志轮转是否正常。
- 磁盘空间不足时服务表现如何。
- 服务重启后日志、临时文件是否正常。

尤其是你项目使用了 systemd 服务管理，部署后还应验证服务崩溃是否能按预期重启，以及日志是否会无限占用磁盘。

不要真的把磁盘写满作为第一步。先检查日志轮转和磁盘告警配置，再在隔离环境模拟受控的磁盘空间不足。

## 十、怎样把这些测试变成真正的排障能力？

这里是我认为最重要的部分：每次测试都应该有一份“故障记录”，而不是只有 JMeter 截图。

建议你以后所有测试都按同一个流程进行。

第 1 步：记录基线

先记录正常情况下的 P95/P99、吞吐量、错误率、CPU、JVM、数据库和 Redis 指标。

第 2 步：只制造一种故障

例如仅让 catalog-service 变慢，或者仅让 Redis 不可用。先避免同时改变多个变量。

第 3 步：收集证据并缩小范围

结合错误日志、Trace、线程栈、连接池、慢 SQL 和资源指标，判断瓶颈在哪一层。

第 4 步：修复并重复测试

记录改了什么、为什么改，然后使用相同负载和故障条件重测。

第 5 步：确认恢复与回归

检查性能是否改善、业务数据是否正确、服务是否恢复，以及原有功能有没有受到影响。

### 线上出现问题时，先查什么？

下面这份速查表值得你保存下来。

| 线上现象          | 第一批检查对象            | 下一步                    |
| ------------- | ------------------ | ---------------------- |
| P95/P99 突然上升  | CPU、线程池、连接池、Trace  | 找出耗时最长的调用和资源等待         |
| 错误率突然升高       | 错误码分布、应用日志、网关日志    | 区分业务错误、超时、限流和服务不可用     |
| CPU 很高        | 线程栈、GC、热点方法、SQL 负载 | 判断是计算密集、频繁 GC 还是其他资源争用 |
| CPU 不高但请求卡住   | 线程栈、连接池、锁等待、网络调用   | 查阻塞和等待，不要只盯 CPU        |
| 数据库负载升高       | 慢 SQL、执行计划、连接数、锁等待 | 先定位最耗资源的查询或事务          |
| Redis 恢复后仍然很慢 | 缓存命中率、回源流量、数据库连接池  | 检查缓存重建是否冲垮数据库          |
| MQ 积压越来越多     | 生产速率、消费速率、消费错误     | 定位消费瓶颈和失败重试            |
| 重启后数据异常       | 事务、消息、缓存、启动顺序      | 检查重复执行、状态恢复与数据一致性      |
| 只有部分用户失败      | 用户权限、请求参数、特定数据、路由  | 比较成功与失败请求的差异           |

排查时最好始终从一个具体请求开始：找到请求时间、接口、错误码和 traceId，再沿着网关、业务服务、Feign、数据库或 MQ 的链路向下追踪。

## 十三、真实生产环境还有一个重要区别

你现在是在自己的学习项目中做实验，能够控制请求量、修改代码和重启服务。但真实生产环境通常还有更多约束：

- 不能随意停服务、删除缓存或修改数据库索引。
- 不能把所有真实用户的流量当成压测流量。
- 不能因为排查问题而随意关闭限流、熔断或鉴权。
- 可能存在多个版本、多台机器和不同配置。
- 数据恢复、回滚和业务补偿必须经过验证。

因此建议你将测试分为三个环境：

| 环境     | 主要用途                      |
| ------ | ------------------------- |
| 本地环境   | 快速复现、单元测试、事务和边界条件实验       |
| 独立测试环境 | JMeter 压测、故障注入、服务重启、MQ 积压 |
| 生产环境   | 以观测和诊断为主；未经审批不做破坏性实验      |

如果将来确实需要在生产环境验证容量，应该先设定负载上限、停止条件、监控和回滚方案，并获得相应授权。

## 最后，我最希望你掌握的能力

不是背出“Redis 缓存雪崩怎么解决”，而是当线上突然出现问题时，你能完成以下闭环：

1. 发现异常： 是吞吐下降、延迟上升，还是错误率突然增加？
2. 缩小范围： 是网关、Java 服务、MySQL、Redis，还是 MQ？
3. 拿到证据： 日志、Trace、线程栈、连接池和数据库状态能否相互印证？
4. 复现根因： 能否在测试环境用可控条件重现问题？
5. 实施修复： 是否理解修复原理和可能的副作用？
6. 验证恢复： 指标、业务数据和整条调用链是否恢复正常？

你已经有 JMeter 测试文档，也已经接触缓存一致性、Sentinel、Feign 和 Zipkin。下一步不必急着再添加更多中间件，而是从上面选一个问题，真正完成一次“发现异常—定位根因—修改代码—回归验证”的全过程。

我最建议你先做的实验是：MySQL 连接池饱和 + 慢 SQL 定位。 因为它能同时锻炼 JMeter、Spring Boot、数据库监控、日志分析和性能判断能力，也很容易延伸到以后工作中遇到的实际问题。

记住一点：学习项目里复现一次问题，能让你理解一种故障；把证据、根因、修复方案和回归结果完整记录下来，才能逐渐形成可以带到下一份工作的排障能力。
