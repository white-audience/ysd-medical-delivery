## 战役一：慢 SQL 与索引优化（S1-S5）

### 1.1 基本信息

| 项 | 内容 |
|---|---|
| 数据库 | MySQL 8.0.42，`ysd_take_out` |
| 数据量 | 100,025 行；8 个药品分类各约 12.3k~12.7k 行 |
| 演练前索引 | `PRIMARY`、`idx_drug_name(unique)`、`idx_drug_category_id`、`idx_drug_status` |
| 慢日志 | `long_query_time=0.01`，`log_queries_not_using_indexes=ON` |
| 关键基数 | `category_id` 约 12%，`status` 全部为 1（基数=1） |

### 1.2 S1：C 端分类浏览

**SQL**

```sql
select * from drug
where category_id = 12 and status = 1
order by create_time desc;
```

**现象**：平均 **89.2 ms**（125.7 / 69.5 / 71.9），`Rows_examined=12,668`，慢日志 0.125 / 0.070 / 0.072 s。

**执行计划**

| type | key | rows | Extra |
|---|---|---|---|
| `index_merge` | `idx_drug_category_id, idx_drug_status` | 11,279 | `Using intersect; Using where; Using filesort` |

**定位过程**

1. `idx_drug_status` 基数=1，却扫了约 100,014 行，对结果没有过滤贡献。
2. `category_id=12` 只筛掉约 12%，仍返回 12,668 行，`select *` 需要 12,668 次回表。
3. 新增复合索引后优化器**仍然不选**：`possible_keys` 已包含新索引，但 `key` 仍是两个单列索引，filesort 仍在。
4. 用 `FORCE INDEX (idx_drug_cat_status_time)` 诊断：实际 **16.5 ms**，`Backward index scan`；`SET optimizer_switch='index_merge=off'` 后优化器改选复合索引。
5. 根因：优化器估算 index_merge `cost=2360`，复合索引 `cost=2446`，低估了 status 分支扫 10 万行 + intersect + 回表的代价。

**修复**

```sql
ALTER TABLE drug
  ADD INDEX idx_drug_cat_status_time (category_id, status, create_time),
  ALGORITHM=INPLACE, LOCK=NONE;

ALTER TABLE drug
  DROP INDEX idx_drug_category_id,
  ALGORITHM=INPLACE, LOCK=NONE;

ANALYZE TABLE drug;
```

**回归结果**

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 客户端 3 次平均 | 89.2 ms | **33.9 ms** |
| T3 复测 | — | 38.2 ms |
| EXPLAIN | index_merge + filesort | `type=ref, key=idx_drug_cat_status_time, Extra=Backward index scan` |
| EXPLAIN ANALYZE 服务端 | 57 ms | **16.6 ms** |

**结论**：删除被复合索引最左前缀覆盖的冗余单列索引，才能让优化器放弃 index_merge。`FORCE INDEX` 只用于诊断，不应作为最终方案。接口本身无分页，仍是遗留问题。

### 1.3 S2：管理端药品分页（前导通配 LIKE）

**SQL**

```sql
select d.*, c.name as categoryName
from drug d left outer join category c on d.category_id = c.id
where d.name like concat('%','测试药品_1000','%') and d.status = 1
order by d.create_time desc
limit 0,10;
```

**现象**

| 查询 | 平均耗时 | 说明 |
|---|---|---|
| 关键词分页 | **101.6 ms** | `Rows_examined=100,045` |
| count | 83.7 ms | 另扫一遍 10 万行 |
| 默认首页（无筛选） | 52.8 ms | `type=ALL` |
| 选择性关键词「阿莫西林」 | 97.4 ms | 只命中 1 条，仍近 100 ms |

**执行计划**：`ref idx_drug_status`，估算 rows=49,454，实际扫描 100,025 行，`Using filesort`。

**判断**

1. 前导通配 `%关键词%` 让 `idx_drug_name` 完全失效。
2. `idx_drug_status` 基数=1，优化器却选择它做 10 万次索引查找 + 回表。
3. 对照实验：`IGNORE INDEX (idx_drug_status)` 走全表扫描仅 **56.2 ms**，比走 status 索引快近一倍。
4. join 不是瓶颈（category 只有 10 行，`eq_ref` 约 0.02 ms）。

**最终选择：不新增 B-Tree 索引。** 在 `%x%` 面前没有可用起点；强行加 `create_time` 索引只对默认首页有效，对选择性关键词可能更差。根治方向是 FULLTEXT/ES 或搜索引擎，且 count 与分页各扫一遍的问题需要单独治理。

### 1.4 S3：AI 问诊按名称/症状搜索

**SQL**

```sql
SELECT id, name, prescription_type, manufacturer, approval_number,
       indications, contraindications, status
FROM drug
WHERE status = 1
  AND (name LIKE CONCAT('%','头痛','%') OR indications LIKE CONCAT('%','头痛','%'))
ORDER BY prescription_type ASC
LIMIT 10;
```

**现象**：平均 **104.7 ms**，`Rows_examined=100,026`，只返回 1 行。

**执行计划**：`ref idx_drug_status`，rows=49,454，`Using where; Using filesort`。

**诊断与实验**

1. 与 S2 同因：低基数 `idx_drug_status` 让优化器扫 10 万行再回表。
2. `IGNORE INDEX (idx_drug_status)` 全表扫描平均 **41.2 ms**，快 2.5 倍。
3. FULLTEXT + ngram 实验：
   - 自然语言模式：约 1.1 ms，但召回变宽（「阿莫西林胶囊」LIKE 命中 1 条，自然语言模式命中 4 条）。
   - 布尔短语模式 `"关键词"`：**0.65 ms**，4 组样例与 LIKE 命中完全一致。
   - 首次建索引 `LOCK=NONE` 报 `ERROR 1846`，改用 `LOCK=SHARED` 成功。
4. 因为当前 Mapper 仍是 LIKE，FULLTEXT 不会被业务使用，实验索引最终删除。

**最终修复**：将 `idx_drug_status` 设为 INVISIBLE，让优化器退回全表扫描：

```sql
ALTER TABLE drug ALTER INDEX idx_drug_status INVISIBLE;
```

S3 耗时从 104.7 ms 降到 **55.3 ms**。

### 1.5 S4 / S5：对照场景

| 场景 | SQL 要点 | 结果 | 结论 |
|---|---|---|---|
| S4 药品组合详情 | `drug_combo_item.combo_id = ?` left join `drug.id` | **0.66 ms**，`ref + eq_ref` | 正确索引下的理想 join；无需变更 |
| S5 工作台药品总览 | `select count(id) from drug where status=1` | **13.8 ms**，`Using index` | 覆盖索引扫描，不回表；无需新增索引 |

`idx_drug_status` INVISIBLE 后 S5 为 13.1 ms，基本持平；这验证了该索引对 S5 几乎没有贡献。

### 1.6 汇总

| 场景 | 操作 | 实测收益 | 是否采纳 |
|---|---|---|---|
| S1 分类浏览 | 新增 `idx_drug_cat_status_time`，删除 `idx_drug_category_id` | 89.2 → 33.9 ms；服务端 57 → 16.6 ms | **采纳** |
| S2 关键词分页 | 不加 B-Tree | 无索引收益；`IGNORE INDEX` 对照 101.6 → 56.2 ms | 不采纳 |
| S3 模糊搜索 | `idx_drug_status` INVISIBLE | 104.7 → 55.3 ms | **采纳** |
| S3 FULLTEXT | `ft_drug_name_indications` | 104.7 → 0.65 ms（布尔短语） | 实验后删除，需改 Mapper 才能上 |
| S4 组合详情 | 沿用现有索引 | 0.66 ms | 无需变更 |
| S5 状态计数 | 沿用现有索引 | 13.8 ms | 无需变更 |

### 1.7 经验

1. **前导通配 LIKE 没有 B-Tree 起点**：`%xx%` 只能全表扫描或走搜索引擎。
2. **低基数索引比全表扫描更慢**：`status` 基数=1 时，索引查找 + 回表是纯负收益。
3. **优化器会选错索引**：不要只看 `possible_keys`，要看 `key`、`rows`、`Extra` 和实际耗时。
4. **`FORCE INDEX`/`IGNORE INDEX` 是诊断工具**：用来验证“换计划会不会更快”，不要直接作为生产方案。
5. **冗余索引会反过来误导优化器**：`idx_drug_category_id` 不删，index_merge 就一直存在。
6. **索引优化不等于接口优化**：S1 一次返回 1.2 万行，S2 count 与分页各扫一遍，都需要代码/分页/搜索引擎层面的改造。

## 战役二：并发安全与唯一索引兜底（T22）

### 2.1 基本信息

| 项 | 内容 |
|---|---|
| 接口 | `POST /user/shoppingCart/add`（经网关 9000） |
| 请求体 | `{"drugId": 46}` |
| 压测工具 | JMeter 5.6.3，`jmeter/plans/t22-cart-race.jmx` |
| 并发设计 | **50 线程**、Ramp 1s、`Synchronizing Timer` 一次性释放 50 线程、Loop=1 |
| 代码路径 | `ShoppingCartServiceImpl.addShoppingCart` |

### 2.2 故障假设

`addShoppingCart` 是典型的 **check-then-act**：

```text
1. SELECT * FROM shopping_cart WHERE user_id=? AND drug_id=?
2. 存在 → UPDATE number = number + 1
3. 不存在 → INSERT 一行
```

步骤 1 和步骤 3 之间没有唯一约束兜底。50 个线程同时查到“不存在”，就会同时执行 INSERT。

### 2.3 复现结果

- 50 个并发请求同时加购 `user_id=4, drug_id=46`。
- 数据库中同一 `(user_id, drug_id)` 出现 **50 条重复行**。
- 接口返回成功，但从业务语义看，购物车里同一药品应该只有 1 行。

这就是“接口成功 ≠ 数据正确”的典型案例：数据库没有报错，业务数据已经脏了。

### 2.4 根因

| 层级 | 问题 |
|---|---|
| 应用层 | 先查后写，存在竞态窗口 |
| 数据库层 | `shopping_cart` 只有主键，没有 `(user_id, drug_id)` 唯一约束 |
| 并发层 | 50 个请求同时通过“不存在”判断 |

### 2.5 修复：不改代码，先用唯一索引兜底

**第 1 步：清理历史重复行**（保留每组最小 id，重复行是竞态脏数据，不做数量累加）

```sql
DELETE sc1
FROM shopping_cart sc1
JOIN shopping_cart sc2
  ON sc1.user_id = sc2.user_id
 AND sc1.drug_id  = sc2.drug_id
 AND sc1.id > sc2.id
WHERE sc1.drug_id IS NOT NULL;
```

**第 2 步：建立唯一索引**

```sql
ALTER TABLE shopping_cart
  ADD UNIQUE KEY uk_user_drug (user_id, drug_id),
  ALGORITHM=INPLACE, LOCK=NONE;
```

### 2.6 回归验证

- 再次用同样的 50 并发压测。
- 结果：`SELECT COUNT(*) FROM shopping_cart WHERE user_id=4 AND drug_id=46;` = **1**。
- 实测残留行 `number=2`：说明唯一索引生效后，后续请求走的是 `UPDATE number+1` 分支，没有再插入重复行。

### 2.7 结论与副作用（重要）

1. **唯一索引是并发正确性的最后一道防线**：应用层的 check-then-act 仍可能并发，但数据库不会再接受重复行。
2. **数据正确 ≠ 接口全部成功**：并发 insert 的失败方会收到 `DuplicateKeyException`，当前全局异常处理没有专门捕获，可能返回 500。若要所有请求都成功，需要：
   - `INSERT ... ON DUPLICATE KEY UPDATE number = number + 1`，或
   - 捕获 `DuplicateKeyException` 后重试一次 UPDATE。
3. **组合加购未被覆盖**：`(user_id, drug_id)` 在 `drug_id IS NULL`（药品组合）时不生效。组合并发如需保护，应另加 `uk_user_combo(user_id, combo_id)`。
4. **写入成本**：唯一索引会增加少量写入维护成本，但相对 50 行重复数据带来的业务问题，这个代价可以接受。

## 战役三：死锁排查与事务回滚（T08 / T09）

### 3.1 T08：交叉更新导致死锁

**基本信息**

| 项 | 内容 |
|---|---|
| 表 | `orders` |
| 数据 | `id=6`、`id=7`（真实存在） |
| 方式 | 两个独立 MySQL 会话，`SELECT ... FOR UPDATE` 只加锁不改数据 |
| 脚本 | `docs/05-测试与压测/靶场脚本/t08-deadlock-session-a.sql` / `b.sql` |

**复现步骤**

```sql
-- 会话 A
START TRANSACTION;
SELECT id,status FROM orders WHERE id=6 FOR UPDATE;

-- 会话 B
START TRANSACTION;
SELECT id,status FROM orders WHERE id=7 FOR UPDATE;

-- A 等 B 锁住 7 后执行（阻塞）
SELECT id,status FROM orders WHERE id=7 FOR UPDATE;

-- B 再执行（触发死锁）
SELECT id,status FROM orders WHERE id=6 FOR UPDATE;
```

**现象**

- 会话 B 报错：`ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction`
- InnoDB 自动回滚其中一个事务（本次实测为 B）。
- 会话 A 解除阻塞，拿到 id=7。
- `SHOW ENGINE INNODB STATUS` 的 `LATEST DETECTED DEADLOCK` 段能看到两个事务各自持有的锁与等待的锁。

**根因**：两个事务以相反顺序请求同一组行锁，形成循环等待。

**修复/预防**

1. 统一加锁顺序（例如永远按主键升序处理）。
2. 缩短事务，把非数据库操作移出事务。
3. 为过滤条件补合适索引，减少锁扫描范围。
4. 死锁重试必须配合幂等，避免重复扣减/重复建单。

**收尾**：两个会话都执行 `ROLLBACK;`，确认 `information_schema.innodb_trx` 为空。

证据：`evidence/T08-session-b-20261020.log`、`evidence/T08-innodb-status-20261020.txt`

### 3.2 T09：事务回滚与部分失败

**基本信息**

| 项 | 内容 |
|---|---|
| 接口 | `POST /user/order/submit` |
| 用户/地址 | `user_id=4`，`address_book_id=2` |
| 事务 | `OrderServiceImpl.submitOrder` 上的 `@Transactional(rollbackFor = Exception.class)` |
| 注入点 | `orderDetailMapper.insertBatch(...)` 之后、`shoppingCartMapper.deleteByUserId(...)` 之前 |
| 基线计数 | `orders=33`、`order_detail=40`、`cart=1` |

**故障注入**

```java
orderDetailMapper.insertBatch(orderDetailList);

if (failOrderDetail) {
    throw new IllegalStateException("T09 fault-injection: fail after order_detail insert, before cart cleanup");
}

shoppingCartMapper.deleteByUserId(userId);
```

**现象**

- 请求返回 HTTP 500。
- 服务端日志出现 `T09 fault-injection`。
- 立即查库：

| 表 | 失败后计数 | 结论 |
|---|---|---|
| `orders` | 33（不变） | `orderMapper.insert` 已回滚 |
| `order_detail` | 40（不变） | `insertBatch` 已回滚 |
| `shopping_cart` | 1（不变） | 未被清空 |

**结论**

1. 本地数据源上的 `@Transactional` 能完整覆盖订单、明细、购物车三个写操作。
2. **跨服务不在同一事务**：第 1 步是 Feign 查地址簿，order 服务的本地事务无法回滚 user 服务的数据；跨服务一致性需要幂等/补偿/事务消息。
3. 本项目 `submitOrder` 内不发 MQ；MQ 与 DB 的原子性问题在 `paySuccess`，不在下单。
4. 验证完成后，注入代码与配置已删除，服务已重新打包。

证据：`evidence/T09-baseline-20261020.txt`、`evidence/T09-verify-20261020.txt`

## 战役四：连接池耗尽（T06）

### 4.1 基本信息

| 项 | 内容 |
|---|---|
| 服务 | `ysd-order-service` 8085 |
| 连接池 | Druid |
| 靶场参数 | `initial-size=5`、`min-idle=5`、`max-active=5`、`max-wait=5000ms` |
| 压测接口 | `GET /user/order/historyOrders?page=1&pageSize=10`（一次请求含分页 + 最多 10 条明细查询） |
| 压测设计 | **50 线程**、Ramp 1s、持续施压（JMeter 手动停止） |

### 4.2 现象

| 指标 | 实测 |
|---|---|
| `MaxActive` | 5 |
| `ActiveCount` | 打满到 **5** |
| `WaitThreadCount` | 峰值 **35**（线程在 `DruidDataSource.getConnection` 排队） |
| 请求结果 | 大量 **500**，日志出现 `GetConnectionTimeoutException` / `wait millis 5000` |
| Druid 累计指标（压测后抓取） | `ActivePeak=5 @ 2026-10-21 18:11:41`；`NotEmptyWaitCount=145,665`；`NotEmptyWaitMillis=3,303,231`；`ErrorCount=48` |

> `NotEmptyWaitCount / NotEmptyWaitMillis` 是 Druid 启动以来的累计值，包含多轮压测；不要把它当成单次请求的等待时间。

### 4.3 根因

1. 连接池只有 5 个连接，50 个并发请求同时需要连接。
2. `historyOrders` 一次请求会执行分页 count、分页查询和多条明细查询，连接占用时间被放大。
3. 拿不到连接的线程进入等待队列；`max-wait=5000` 到期后快速失败，表现为 500。
4. Tomcat 工作线程被阻塞在拿连接上，接口整体变慢；这与 CPU 高不高没有必然关系。

### 4.4 结论

1. **连接池大小要匹配数据库承载力**：盲目调大 `max-active` 只是把压力转移给 MySQL，可能让 DB 更慢。
2. **`max-wait` 是自我保护**：有限等待 + 快速失败，避免 Tomcat 线程无限堆积；代价是部分请求返回 500。
3. **先找连接被谁占用**：慢 SQL、长事务、连接泄漏、一次请求多次查询，都比“把池调大”更值得先查。
4. **观测口径**：`ActiveCount ≈ MaxActive` 且 `WaitThreadCount` 持续上升 = 池饱和；停止施压后两者应回落。
5. 生产环境不应长期开启 Druid StatViewServlet（`admin/admin` 会暴露 SQL 与连接信息）；应使用 Micrometer/Prometheus 指标。

### 4.5 恢复

- 已删除 `max-active=5`、`max-wait=5000`、`stat-view-servlet`、`web-stat-filter` 等临时配置。
- 服务已重新打包并重启，`/druid/login.html` 返回 **404**，接口恢复正常。
